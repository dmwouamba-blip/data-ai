1. Executive Summary

Perspective of the Healthcare Platforms Data Architect

This document presents a controlled demonstration of how the Diabetes Care Platform (DCP) can turn heterogeneous healthcare, device, patient-generated, consent, compliance and regulatory information into governed Data Products. The purpose is not to simulate clinical truth or claim production readiness. It is to make the target platform flow tangible, testable and reviewable before real data, production integrations or regulated decisions are introduced.

The propositionUse deterministic synthetic data to validate the architecture, engineering workflow, governance controls and Data Product boundaries from source files to business consumption.

Why this matters to Sponsors, the CIO and platform leadership

Sponsors and business leaders

Connect investment to use cases

The demo provides a shared view of how platform capabilities support patient glucose timelines and summaries, self-management events, device and synchronization status, consent monitoring, healthcare compliance and selected regulatory operations. It enables scope, ownership and release discussions using executable evidence rather than presentation-only concepts.

CIO, CDO and architecture leadership

Validate the platform pattern

The landing-first flow demonstrates separation of source evidence, raw ingestion, canonical transformation and curated Data Products. Unity Catalog objects, numbered schemas, an auditable landing volume, deterministic runs and validation gates provide a concrete basis for evaluating governance, traceability, replay and operational control.

Privacy, quality, security and regulatory stakeholders

Review controls before production

Consent state and propagation, compliance assessments, regulatory submissions and authority interactions are represented as synthetic test scenarios. This allows control owners to challenge purpose, access, lineage, quality, exception handling and evidence requirements without using real patient, employee, product or authority data.

Business use cases represented in this demo

Patient and clinical data productsGlucose timelines and daily summaries, patient self-management events and a foundation for clinical review and population-oriented analytics.
Device and platform operationsDevice state, synchronization outcomes and failure scenarios that support operational monitoring and engineering investigation.
Consent and trusted data useCurrent consent state, event history and downstream propagation status to test traceability, failures and acknowledgement behavior.
Compliance and regulatory operationsControl assessments, product master, submission tracking and authority interactions for representative monitoring and workflow scenarios.
Governed Data Product MarketplaceA portfolio view that distinguishes implemented, partial and model-only coverage so that discoverability does not get confused with technical readiness.
Quality and release evidenceGolden expectations, deterministic datasets and explicit edge cases for repeatable regression, reconciliation and deployment gates.

What the Data Engineer receives

A runnable sequence for creating the Unity Catalog foundation, generating files into /Volumes/dcp_synth/00_config/00_landing, ingesting CSV, JSON and Parquet into Bronze, transforming selected entities through Silver and Gold, registering Data Products and executing Golden Tests.

  • Repeatability: fixed parameters, stable synthetic keys and a deterministic run identifier.
  • Traceability: source catalog, landing paths, format metadata, manifest and ingestion-audit structures.
  • Operational safety: isolated non-production execution, stop rules, count checks and explicit replay boundaries.
  • Engineering boundary: implemented objects are separated from partial and model-only products; templates still require environment, security, performance and policy validation.

Architect recommendation and decision boundary

Use this demo as a vertical architecture and engineering proof point. The immediate success criterion is a reproducible path from synthetic landing files through governed transformations to selected Data Products and test evidence. Do not interpret successful execution as clinical validation, regulatory approval or production certification. Before any production release, accountable owners must approve source contracts, semantics, allowed purposes, security controls, quality thresholds, service objectives, operating model and release evidence.

Recommended leadership decision: approve the demo as a non-production validation baseline and use its evidence to select the first production-controlled vertical slice, with named Business, Data Product, Privacy, Security, Quality, Architecture, Engineering and Operations owners.

7. 02_generate_healthcare_landing.py

Erzeugt Healthcare-Testdaten ausschließlich als Dateien im Landing-Volume. CSV wird für Masterdaten, JSON für Eventdaten und Parquet für sehr große CGM-Zeitreihen verwendet.

Python / PySpark
# DEPLOYABLE TEMPLATE | Databricks Python notebook
from pyspark.sql import functions as F
p = spark.table('dcp_synth.`00_config`.synthetic_parameters').first()
root, seed = p.landing_root, p.deterministic_seed
run_id = f'run_{p.fixed_generated_at:%Y%m%dT%H%M%S}'
patients = (spark.range(1, p.patient_count + 1)
 .select(F.format_string('SYN-P-%04d', F.col('id')).alias('patient_id'),
 F.format_string('Synthetic-%04d', F.col('id')).alias('display_name'),
 F.expr("date_add(date'1955-01-01', pmod(xxhash64(id, 42), 18000))").alias('birth_date'),
 F.element_at(F.array(*[F.lit(x) for x in ['DE','CH','FR','IT']]), 1+F.pmod('id',F.lit(4))).alias('country'),
 F.lit('SYNTHETIC').alias('data_class'), F.lit(run_id).alias('_run_id')))
(patients.coalesce(1).write.mode('overwrite').option('header',True)
 .csv(f'{root}/SRC-11/patient_master/{run_id}'))
# CGM uses Parquet to avoid impractically large text files while preserving file-first ingestion.
times = spark.sql(f"SELECT explode(sequence(timestamp'{p.history_start_date} 00:00:00', timestamp'{p.history_end_date} 23:55:00', interval 5 minutes)) event_time")
cgm=(patients.select('patient_id').crossJoin(times)
 .withColumn('reading_id',F.sha2(F.concat_ws('|','patient_id',F.col('event_time').cast('string')),256))
 .withColumn('glucose_mmol_l',F.round(F.greatest(F.lit(2.2),F.least(F.lit(22.0),F.lit(6.8)+(F.pmod(F.xxhash64('patient_id','event_time',F.lit(seed)),F.lit(1000))/1000-.5)*2.4)),1))
 .withColumn('source_id',F.lit('SRC-01')).withColumn('_run_id',F.lit(run_id)))
(cgm.write.mode('overwrite').partitionBy('_run_id').parquet(f'{root}/SRC-01/cgm_readings'))
# Smaller event streams are JSON/NDJSON.
(patients.select('patient_id',F.lit('SRC-16').alias('source_id'),F.lit(run_id).alias('_run_id'))
 .write.mode('overwrite').json(f'{root}/SRC-16/device_events/{run_id}'))
Idempotenz: Jeder Pfad enthält eine feste run_id. Ein Wiederholungslauf überschreibt nur denselben synthetischen Run und erzeugt keine Duplikate durch wechselnde Zeitstempel.

from pyspark.sql import functions as F
p=spark.table('dcp_synth.`00_config`.synthetic_parameters').first()
root=p.landing_root; run_id=f'run_{p.fixed_generated_at:%Y%m%dT%H%M%S}'

consent=(patients.select('patient_id').crossJoin(scopes)
 .withColumn('consent_event_id',F.sha2(F.concat_ws('|','patient_id','consent_scope',F.lit('GRANT')),256))
 .withColumn('new_state',F.lit('GRANTED')).withColumn('source_id',F.lit('SRC-14'))
 .withColumn('_run_id',F.lit(run_id)))
consent.write.mode('overwrite').json(f'{root}/SRC-14/consent_events/{run_id}')
controls=(spark.range(1,61).select(F.format_string('CTL-%03d','id').alias('control_id'),F.lit('ACTIVE').alias('lifecycle_status'),F.lit(run_id).alias('_run_id')))
controls.coalesce(1).write.mode('overwrite').option('header',True).csv(f'{root}/SRC-25/compliance_controls/{run_id}')
submissions=(spark.range(1,101).select(F.format_string('SUB-%04d','id').alias('submission_id'),F.lit('ON_TRACK').alias('risk_status'),F.lit(run_id).alias('_run_id')))
submissions.write.mode('overwrite').json(f'{root}/SRC-21/regulatory_submissions/{run_id}')
manifest=[('SRC-11','CSV',f'{root}/SRC-11/patient_master/{run_id}'),('SRC-01','PARQUET',f'{root}/SRC-01/cgm_readings'),('SRC-16','JSON',f'{root}/SRC-16/device_events/{run_id}'),('SRC-14','JSON',f'{root}/SRC-14/consent_events/{run_id}'),('SRC-25','CSV',f'{root}/SRC-25/compliance_controls/{run_id}'),('SRC-21','JSON',f'{root}/SRC-21/regulatory_submissions/{run_id}')]

19.5 Gold implementation

SQL · 11_patient_diabetes_360.sql
-- DEPLOYABLE TEMPLATE | synthetic non-production only
USE CATALOG dcp_synth;
CREATE OR REPLACE VIEW `03_gold`.dp26_patient_diabetes_360 AS
WITH latest_glucose AS (
  SELECT * EXCEPT(rn) FROM (
    SELECT patient_id, reading_id, event_time, glucose_mmol_l, device_id,
           source_id, ingested_at, quality_status,
           row_number() OVER (PARTITION BY patient_id ORDER BY event_time DESC, ingested_at DESC) rn
    FROM `02_silver`.glucose_readings WHERE quality_status='PASS'
  ) WHERE rn=1
), current_consent AS (
  SELECT patient_id,
         collect_set(named_struct('scope',consent_scope,'purpose',purpose,
           'recipient',recipient,'state',current_state,'effective_at',effective_at,
           'consent_event_id',consent_event_id)) consent_states,
         bool_and(current_state='GRANTED') consent_validated
  FROM `03_gold`.dp10_patient_consent_current GROUP BY patient_id
), latest_device AS (
  SELECT * EXCEPT(rn) FROM (
    SELECT patient_id,device_id,event_time last_sync_at,firmware_version,sync_status,
           row_number() OVER (PARTITION BY patient_id ORDER BY event_time DESC) rn
    FROM `01_bronze`.device_events
  ) WHERE rn=1
)
SELECT p.patient_id patient_key,p.birth_date,p.country,p.diabetes_type,p.therapy_profile,
       g.reading_id latest_glucose_observation_id,g.event_time latest_glucose_at,
       g.glucose_mmol_l latest_glucose_mmol_l,g.device_id,d.sync_status,d.last_sync_at,
       d.firmware_version,c.consent_states,coalesce(c.consent_validated,false) consent_validated,
       greatest(g.ingested_at,d.last_sync_at) generated_at,'1.0.0' product_version,
       'Highly Restricted' data_classification,g.source_id latest_glucose_source,
       p._run_id lineage_run_id
FROM `02_silver`.patient p
LEFT JOIN latest_glucose g ON p.patient_id=g.patient_id
LEFT JOIN latest_device d ON p.patient_id=d.patient_id
LEFT JOIN current_consent c ON p.patient_id=c.patient_id;

19.8 Consumer usage

SQL and dashboards
Consume approved presentation views, select explicit columns, display freshness and unit, and never use visual filters as security.
API and event consumers
Validate payloads against the pinned schema version; reject or quarantine invalid records; carry product version, purpose, quality and lineage.
Data science
Use the approved analytical or feature port, record the contract version, preserve event time and never train on purpose-incompatible data.
GenAI and RAG
Filter by approved purpose and consent before retrieval, minimize PHI, record grounding lineage and apply evaluation and human-review controls.

19.9 Usage workflow

  1. Resolve the product and contract version from the Data Product Marketplace.
  2. Request access using an approved consumer identity, purpose and patient scope.
  3. Select the correct output port: governed SQL view, presentation view, API/event payload or feature set.
  4. Validate payloads against the JSON Schema before processing or publication.
  5. Check quality status, freshness, consent decision, source timestamps and lineage.
  6. Process only permitted fields and preserve the contract version in downstream metadata.
  7. Monitor failures, schema drift, stale data, access events and consent propagation.
  8. Revalidate after schema, purpose, permission, semantic or upstream-contract changes.
